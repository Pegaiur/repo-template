# commit-convention

只负责一次原子提交：检查 → 验证 → 审查 → 精准暂存 → 中文约定式提交 → 报告。发版、版本号、tag 与分支清理由 `release-workflow` 编排；其确定提交范围与时机后，可复用本技能完成原子提交，本技能不改变发版决策。

## 提交信息规范

前缀 + 具体中文描述。描述回答「做了什么」（why 入正文段，不在标题）。

| 前缀 | 用途 |
|------|------|
| `feat` | 新增功能、模块或业务逻辑 |
| `fix` | 修复 Bug，使失败测试通过 |
| `refactor` | 重构代码，不改变业务行为 |
| `test` | 新增或修改测试用例 |
| `docs` | 更新文档、规范或注释 |
| `chore` | 构建、依赖、版本等杂项 |
| `perf` | 性能优化 |
| `build` | 构建系统或外部依赖变更 |
| `ci` | CI 配置变更 |
| `revert` | 回滚某次提交 |

- 每个提交必须有具体、可读的中文描述，禁止无意义的「update」「fix bug」。
- 若一次提交涉及多个领域，选主导领域作前缀。
- `merge` 与 `chore(release)` 由 `release-workflow` 产生，不作为普通提交的默认选择。

## 执行流程

1. **状态检查**：`git status` 读取工作区变更文件列表。
2. **变更分析**：判断提交类型，按单一关注点分组（不同类型变更分多次提交）。
3. **信息生成**：按规范拼装 commit message（前缀 + 中文描述，why 入正文）。
4. **验证**：先运行 `git diff --check` 拦截尾随空白与文件末尾新增空行；再运行匹配变更范围的测试/类型检查（按仓库验证路由，如受影响模块的 test 命令，命令清单见 scripts/gates.mjs）并确认通过。
5. **审查**：见下方「审查」。
6. **精准暂存**：`git add <目标文件>`（按名添加），不用 `git add .` 或 `git add -A`；暂存前确认暂存区仅含目标文件，暂存后运行 `git diff --cached --check`，失败时先修复并重新精准暂存。
7. **提交**：`git commit -m "前缀(领域): 中文描述"`。
8. **报告**：简述提交内容、文件数、审查结论。

## 审查（能力探测）

提交前执行审查，检查以下维度：安全性（密钥/Token/密码/内网地址）、逻辑正确性（边界、空值）、一致性（风格/命名/模式）、完整性（TODO/调试代码残留）、破坏性（公共接口/配置/输出格式变更）。

- **审查代理类型（强制）**：独立审查必须使用「审查/评估型」子代理——具备只读文件访问与独立技术评估能力（逐条事实核查、逻辑/等价性验证、风险与设计评价、输出结构化结论如 PASS/FAIL/风险+评分）。**禁止**用通用搜索/编码型子代理代行：其只做信息召回、不产出评估结论，总结口径不构成审查证据。
- **选择方式**：按宿主可用子代理的能力描述挑选审查型（特征：描述含「审查/评估/评价/review/evaluate」语义；多个可选时优先结论最结构化者）。不依赖任何宿主的私有 agent 名称，不同环境以对等能力映射。
- **审查输入与处置**：向审查代理提供本次变更的 diff 范围、涉及文件路径与变更意图（why），要求其从磁盘读取实际文件核对（不得凭摘要断言）；按结论继续或先修复阻塞项，审查结论与修复结果随提交报告一并说明。
- 宿主完全不支持隔离子代理时：按同一检查表执行本地自审，并在报告中**明确标注降级**（「本地自审，未经独立审查」）。

## 多文件提交策略

- **单一关注点**：一次提交只含同一类型变更；feat 与 fix 并存时分两次提交。
- **原子化**：跨层变更按步骤拆分——先数据/模型（`feat`），再测试（`test`），最后表现层（`feat`）。
- **关联合并**：同一功能的数据模型 + 业务逻辑可合入一次 `feat`。

## 注意事项

- 提交前确认所有变更文件已保存；严禁提交含密钥/Token/密码的文件。
- git config 首次设置（编码/分页）见 AGENTS.md「Git 环境」段（仓库约定，不依赖用户级规则），本技能不处理。
- 若项目有 pre-commit hook，确保提交能通过。
