# tech-debt-governance

对分支/工作范围的既有代码做系统化技术债治理：先扫描定位，再交叉审查纠偏，然后按 ROI 分批收敛，逐批验证提交。实战经验：最终只做 ROI 判定为"立即"的收敛，其余记 backlog，避免为抽象而抽象。

## 触发场景

- 用户要求对分支工作范围做技术债扫描 / 质量审查 / 代码健康检查
- 用户提到"重复实现、大文件大函数、强耦合"等关键词
- 用户要求评估修复优先级 / ROI / 工程量，或要求分批修复并提交

## 阶段 0：界定范围

1. `node scripts/tasks/git/head-diff.mjs --merge-base <主分支> --json`（或 `--base <基线>`）取变更文件清单与 summary（基线语义由 lib/git.mjs 封装，避免手跑 git 失真；大 patch 自动落盘 dev-temp/runs）。
2. 用 head-diff 文件清单按行数排序识别大文件（生产源码与测试/文档分离，避免模板/DSL 行数虚高干扰）。
3. 明确本分支主题与既有约束（spec/ADR/实施笔记），后续所有评估挂靠这些上下文。
4. **精读分支涉及的实施笔记（`*-notes.md`）**：抽取「决策偏离 / 权衡记录 / 意外发现 / 阻塞与解决」段中明示的妥协、未来偿还与已知边界，产出「笔记信号清单」（精确到 文件:行号 + 段名 + 条目标题 + 命中关键词）作为阶段 1 扫描线索。实战验证：实施记录是技术债信号的高密度来源（如"消费方须切片解析 stdout"的记录背后就是一处消费者切片债），跳过它首轮会漏掉实质债项。**降级路径**：spec 已归档时 notes 已合并进 plan 尾部「实施纪要」段——回退扫该段；两处皆无则显式声明「无笔记信号，进入阶段 1」，不允许静默跳过。清单是候选信号、可能过时，交阶段 1/2 核实现状，不盲信。

## 阶段 1：三维度并行扫描

并行拉起 3 个只读研究子代理（只研究不修改），各自独立输出结构化清单（精确到 文件:行号）：

| 代理 | 扫描维度 | 输出要点 |
|------|----------|----------|
| A | **大文件大函数** | >60 行函数清单（文件:行号、函数名、行数降序）；归类（命令式分支过多 / 职责混杂 / 回调状态机过长 / 声明式模板虚高）；重点标注**本分支新增 >80 行**的函数 |
| B | **重复实现** | 逐项验证疑点并给出 是/否 结论：跨端同语义算法（如分页/闭包）、同模块重复查询、参数校验/错误码映射重复、状态渲染回退重复、编排脚本样板 |
| C | **强耦合** | 路由/处理器与数据访问门面缺失、巨型 hook / 上帝对象、内部数据形状被组件直索引、类型双端重复定义、性能基建耦合、依赖方向违规（按仓库分层约定） |

**注入笔记信号清单**：把阶段 0 的清单附原文位置发给三个代理，要求逐项输出「成立 / 已修复 / 部分成立 + 现状证据（文件:行号）」；同一信号查遍全部位置（如某侧消费者切片已修复，须查其姊妹位置）。扫描范围：以 head-diff 变更文件清单为入口，沿「同类位置全查」扩展到关联文件（维度 B 重复实现尤其需要跨文件视野）。

同时主代理亲自精读最核心的 1-2 个文件做交叉验证（子代理结论不可盲信；优先选 diff 增行最多或笔记信号命中最多的文件）。

## 阶段 2：双 agent 交叉审查（强制）

扫描报告产出后，并行拉起两个独立代理：

1. **事实核查**（只读研究子代理）：逐条核查报告的 文件:行号 / 函数存在性 / 重复关系是否真实成立 / 行数声称（行号校验可用 `node scripts/tasks/git/show-file.mjs --sha <commit> --path <file>` 提取原文替代 Read 猜测）；输出修正表（准确 / 部分准确 / 不准确）。重点捕捉：行号偏移、命名错误、已漂移副本（比"重复"更严重的信号）、被遗漏的第三/第四处同类。**追加核对「笔记信号清单」**：笔记声称的妥协/债项在当前代码是否仍成立（笔记可能已被后续提交修复），并主动搜索同一模式的**全部**同类位置（例：一侧切片已修，另一消费侧仍是切片——姊妹问题易漏）。
2. **ROI 评估**（独立评估代理）：对每一项评估 成本（低/中/高）+ 收益（低/中/高）+ 时机（**合并前立即修 / 合并后近期修记 backlog / 不值得修**）；并指出建议方案本身的设计问题（如抽公共模块会破坏测试独立性、纯类型包性质变更、抽象泄漏）。能力探测：宿主支持隔离子 Agent 时启动独立只读评估代理，不支持时由主代理按同一评估维度本地执行并标注降级。

**冲突仲裁**：事实核查为准、修正表先行——先应用修正表（不准确项直接降级/删除），ROI 仅对修正后准确项评估。**backlog 载体固化**：记入对应实施笔记（规则见 `docs/rules/document-lifecycle.md`「实施笔记维护」），标注编号与关闭项。

**注入项目约束**：依赖方向单向（按仓库分层约定）、跨模块共享类型载体、合并门槛（`node scripts/verify.mjs merge` 唯一入口，不复制命令清单）、document-lifecycle「实施笔记维护」、既有测试覆盖。

## 阶段 3：工程量评估

对"近期"批次逐项给出：改动文件数、净增删行、测试回归面、门禁成本（typecheck/test/lint/doc-check 涉及模块数）、设计决策点。明确标注哪些是"删重复为主"的低风险项、哪些是"算法语义迁移"的中风险项。

## 阶段 4：逐批实施与提交

1. **先做 ROI"立即"项**：满足四个条件才够格——成本低、零行为变化、本分支已触碰的文件、既有测试在位。批收尾/合并前跑一次 `node scripts/verify.mjs merge`（门禁唯一入口，命令清单唯一事实源），即收工，不新增测试。
2. 每批实施流程：
   - 修改超 3 个文件前向用户展示变更摘要；
   - 批内验证按 AGENTS.md「运行与验证」路由（仅受影响模块的 typecheck + test），不逐批跑全量 doc-check（verify merge 内含）；
   - 提交前经独立审查（commit-convention 技能强制要求——宿主支持隔离子 Agent → 独立只读审查；不支持 → 本地自审并标注降级），修复阻塞项后提交；
   - 提交必须走 **commit-convention 技能**（禁止裸 git commit），提交信息 `类型(领域): 中文描述`，每批一个提交。
3. **实施笔记补记**：收敛决策补记到对应 `*-notes.md`（document-lifecycle「实施笔记维护」规则，以规则触发条件为准：决策/调整/权衡/意外/阻塞任一发生即记），说明背景/做法/验证/影响；验证数据（测试数、语义等价比对方式）写入供回溯。
4. 收尾执行仓库约定的收尾守卫（如临时文件残留/孤儿脚本/git 编码检查），通过才声明完成。

## 关键纪律（防过度重构）

- **同类位置全查**：修复一个消费者切片 / 平台包装 / 路径拼接时，主动搜索该模式的全部出现位置——姊妹问题往往藏在相邻文件或对应消费侧，只修一处等于留债。分工：阶段 1 负责「报告内疑点的全部位置」，本条负责「修复动作的模式扩散搜索」，后者不重复扫描。
- **不值得修的典型**：三处展示契约不同的重复（统一会改 UI 文案）、单流程+共享状态的自然大函数（拆分纯增间接层）、为 1-2 行薄查询建 Repository（过早抽象）。
- **区分生产债与测试/基建债**：后者成本低收益也低，常可接受。
- **跨底层模块重构不贴合并门禁**：合并前只做本分支已触碰文件内的收敛。
- 收敛方向以"单点持有 + 消费方 re-export 保兼容"优先，避免一次性改名波及所有消费方。
- 协议类型/常量下沉共享模块时守住边界：只沉 wire 契约，不沉内部行形状与预算行为；模块性质变更需同步配套约定文档。
